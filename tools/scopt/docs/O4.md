# scopt O4

scopt O4 is one fixed configuration: every scopt speed optimization that has been shown to
help on trusted sealed captures, and nothing that has not. `scopt optimize -O4` builds it.
The per-item decisions are in `scopt/o4.py`, the timing evidence in `docs/o4-evidence.json`
(written only by `scripts/o4_evidence.py`), and `tests/unit/test_o4_manifest.py` enforces
both. The design and its review are `/data/scfix-o4/design/O4-design.md` (the "design"
below; § numbers refer to it).

"scopt O4" is this configuration. It is not FirmBOLT's `-O4` image build (which built the
packet, uart and cli firmware it was measured on) and not the B3 negative-control oracle
`O4` (`scopt/run/oracles.py`).

## The rule

> "we should have one config that include all of our good things let's call it O4.
> Do that! and O4 remains the best. Note it down as well. Whatever the best speed
> optimizations are there MUST BE included in O4~!" (the user, 2026-11-25)

On WHOPR the user added: "even without profile-guided firmlooper should help identify hot
regions."

Three checkable properties follow from it:

1. **(I) Inclusion.** Every speed optimization that passes the add-on rule (Decision rule,
   below) is in O4.
2. **(B) Best.** In the latest campaign that times a configuration against O4, it is not
   faster than O4 on any workload, or pooled. "Faster" means a Holm-adjusted one-sided test
   at family α = 0.05 (rule BEST).
3. **(D) Decided.** Every registered pass, every firmware-inline mode (built-in or
   installed), every parameter of every pass O4 runs and every runtime setting QEMU reads
   has a recorded decision with evidence in `scopt/o4.py`.

`test_o4_manifest.py` fails when a pass, mode, parameter or `QEMU_SC_*` variable has no
decision (D), when `O4.toml` does not carry exactly the included items (I), and when any
row of the current revision in `docs/o4-evidence.json` is `faster_than_o4` (B).

## Using O4

    scopt optimize <sealed snapshot> -O4 --profile <sealed steady profile> \
        --prep <sealed prep> --elf <exact ELF> \
        --runtime-identity <runtime.json of the QEMU that will run the artifact> \
        --pgo-launch <sealed compiled launch> --store <dir> --json

`-O4` is the packaged `pipelines/O4.toml` (never `$SCOPT_PIPELINES_DIR`), which always
equals the newest frozen revision, now `pipelines/O4-r1.toml`. `--pipeline O4` and
`--pipeline O4-r1` run the same checks.

The QEMU named in runtime.json must be in `scopt/data/qemu_capabilities.json` as member-skip
capable (aacca05, `951775b0…eebc60`). For a binary that is not in the table, first confirm
it has counters revision 4, then pass
`--v6-exe/--v7-trusted-exe/--v7-member-skip-exe sha256:$(sha256sum <that binary> | cut -d' ' -f1)`.
scopt refuses digests the table marks incapable (a1bdec6, `026f8e8b…630295`, and the build
in the a79d340 checkout, `ab3fcecd…f9a63c`), whatever flag names them. The artifact runs only
on the QEMU it was captured with: the v7 runtime signature hashes the executable's identity
(device, inode, size and mtime, and every executable mapping), and QEMU discards a cache
captured by any other binary.

**Inputs.**

- A trusted sealed capture of an icount-off run (`docs/sealed-firmware.md`):
  `prepare_sealed_firmware.py … --trust-user-no-recovery`, then `scopt bundle identity`,
  `fastdyn compile-launch`, the runtime identity and `scopt import`.
- Its sealed steady profile:
  `scopt profile run -c <sealed config> --snapshot S --qemu <capable qemu> --sealed --trusted --phase steady@<marker> --inputs <train input> --out <dir>`.
  The markers of the measured images are packet 0x833e8, uart 0x822fc and cli 0x82fc4.
- `--pgo-launch`, the sealed compiled launch, for the host-inline counted replay. A prep
  with `launch.json`, or with `run.toml` and `fastdyn` on PATH, also works.

**The preflight.** Before any build work, one usage error names every problem:

- O4 is fixed: `--disable`, `--enable`, `--only`, `--params`, a non-`auto` `--pgo-phase`,
  and a pipeline file named `O4` that differs from the packaged one are refused. Copy
  `O4-rN.toml` under another name to experiment.
- `--runtime-identity`, `--prep`, `--elf` and `--profile` are required.
- The profile must be an exact profile of this snapshot (complete, exact dispatch, no
  overflow, chaining disabled) with the steady phase reached, matching it at 0.95 or more.
- The capture must be icount-off and sealed (no `CF_PCREL` entry key). For ordinary
  captures use the SFB+B3 recipe (`docs/b3-passes.md`, configuration c5).
- The runtime QEMU must be capable as above.
- No B3 cost calibration may be active (`SCOPT_B3_CALIBRATION`, or
  `$FASTDYN_ROOT/runs/b3-explore/wp16/calibration.json` with costs other than the built-in
  ones): O4 was measured with the built-in costs.
- The hot-loop host-inline needs a training launch.

**The stage gate.** After the passes run and before anything is published, every O4 pass
(the host-inline native prefix included) must have run to `edited` or `no_change`
(`scopt/run/pass_policy.py`, `gate_status`). firmware-inline's `no_profitable_call`,
`no_eligible_call` and `no_firmware_call` count as `no_change`: a firmware with nothing
worth a region. They do not when a root could not be priced
(`refused:profit_estimate_unknown`: executions unknown or flow not converged). Anything else (for example `missing_profile`, `profile_phase_not_reached`,
`profile_incompatible`, `hot_loop_exact_profile_required`, `guest_image_missing`,
`incomplete_lookup_profile` or `policy_disabled`) rejects the build as
`o4_stage_degraded` with exit status 2, and nothing is published. The JSON result carries
the preflight record (`o4`) and the `effective_configuration`.

**Runtime settings** for every O4 launch (`scopt/o4.py` RUNTIME):

| Setting | Decision | Why |
|---|---|---|
| `QEMU_SC_SEALED` | `=1`, required | the sealed whole-firmware tier |
| `QEMU_SC_TRUSTED` | `=1`, required | trusted record input, needed for trusted v7 |
| icount off (no -icount) | required | the trusted contract (`trusted_icount_active`) |
| QEMU in scopt/data/qemu_capabilities.json | required | counters revision 4 and member skip |
| artifact qemu_sha256 = launched QEMU | required | the runtime signature binds the executable |
| `QEMU_SC_SEALED_SKIP_IRQ` | never (unsafe) | changes the interrupt contract; disables trusted exit and T->T chaining |
| `QEMU_SC_V7_EXPERIMENT` | never | every token restores an older behaviour or ablates a measured default; `no-sealed-sc6` is also unsafe |
| `QEMU_SC_*_STATS` | never when timing | diagnostic counters |
| `QEMU_SC_PROFILE*` | never when timing | qprof collection for training |
| `QEMU_SC_CAPTURE*` | never at an O4 launch | capture instrumentation for the prerequisite capture |
| `QEMU_SC_RESTORE_*` | not used | O4 artifacts ship no `.restore-hints`; never timed on sealed |

The launch also uses `-accel tcg,supercache=<artifact>/cache.sc` and, for timing, the
plugin `libfastdyn.so` with `coverage=0` and `FASTDYN_TIMING=1`.

**Out of scope.** There is no O4 for runs without a profile (B3, which carries the gain,
needs it) and none for the ordinary (non-sealed) tier, where SFB+B3 (c5) is the measured
configuration. `-O4` refuses both.

## FirmLooper and WHOPR

- **WHOPR planner.** O4 keeps it. It never removes a candidate, but its partition order is
  the order in which regions are priced, and through the covered-first sort that order
  changes which roots are admitted. A8 decides the planner.
- **Exhaustive (WHOPR) selection.** Unpriced, it is measured slower (w7, w7bd_b3) and
  excluded. Priced, it is challenger A5 in campaign H.
- **FirmLooper.** It finds task loops without a profile. O4 needs the profile anyway, for
  B3, which carries the gain, so a profile-free O4 is not possible. The user's idea,
  "FirmLooper finds, PGO prices", is challenger C1p and needs no code. Under pricing every
  FirmLooper-only root the probes saw is refused unless the profile saw it called; the one
  admitted root, the 14-call memset, is also admitted by A7, so the union mode A2a lands only
  if A7 or C1p shows a signal.
- **Deferred yields.** Hot-loop regions defer a PendSV that cloned kernel code requests
  just before an ISB to the region exit. The trusted contract (`interrupts = "disabled"`)
  allows that, and every functional check passed. O4-r1 does so at 33 / 2 / 0 edges in
  15 / 2 / 0 regions, after `portYIELD_WITHIN_API` in `xTaskResumeAll` (target 0x80924)
  and `xQueueGenericSend` (0x81ed4, 0x81ef2; uart 0x13f4). Fidelity item I1
  (`isb_boundary = true`) decides whether O4 takes the yield at the ISB instead.

## Compatibility

The O4 pipelines opt the B3 passes in with the pipeline-entry key `enabled = true`. scopt
builds older than that key reject it (strict entry keys), including the editable install in
`/data/trebuchet-clean/FastDyn/scopt-env`. So `O4.toml`, `O4-rN.toml`, the arm files and any
sidecar that records them can be read only by scopt at or after the O4 commit. This is
deliberate: an older tool fails loudly instead of running O4 without B3 (an `x_enabled`
key would have been dropped silently). Existing pipelines never use the key and keep their
pipeline ids.

## How to add a new optimization

1. **Register it.** `test_o4_manifest.py` fails until `scopt/o4.py` has a decision for the
   new pass, mode, parameter or `QEMU_SC_*` variable. Start with EXCLUDED `unmeasured` and
   name its arm.
2. **Write the arm** as the current `O4-rN.toml` plus that one change, under a lowercase
   `o4-…` name (a pipeline named `O4` or `O4-r<digits>` runs the preflight and must equal a packaged revision).
3. **Build it** on the three captures (packet, uart, cli), check the build gates (design
   §3.2: functional check, loader requirement, region links, regions replay, same-bytes
   comparison), then screen it in campaign A and, if it survives, run its head-to-head.
4. **Apply the decision rule** below, compose the accepted items (at most one per group),
   and confirm the composition (B1) and the best-check (B2) in campaign B.
5. **Write `O4-r(N+1).toml`**, point `O4.toml` at it, flip the decisions in `scopt/o4.py`,
   append the revision to `REVISIONS` and set `REVISION`, add the campaign to the evidence
   spec and regenerate `docs/o4-evidence.json` with `scripts/o4_evidence.py build`, and
   update the tables above. A rejected item keeps its numbers in `scopt/o4.py` and here.

If any recorded arm is ever faster than O4, `test_no_recorded_arm_beats_o4` fails until O4
absorbs it or a re-timing against the new revision overturns it.

## Decision rule

The rule was written before any O4 data (design §3.7, verbatim). The pre-registered
implementation is `/data/scfix-o4/driver/decide.py`.

The estimator it computes (design §3.3, verbatim):

**Estimator (pre-registered).** For candidate X on workload w, take each block b except
the burn-in block 0:

    l_b = log( sqrt(T_b(o4) · T_b(o4-aa)) / T_b(X) )

where T_b is the block sum over cases.

- d_w is the Hodges-Lehmann estimate of the l_b, the median of the Walsh averages.
- SE_w is the SD of 20,000 block-bootstrap resamples of d_w, seeded with
  `f"{seed}:{w}:{X}"`.
- Pooled over the workloads where X's bytes differ:
  d = Σ(d_w / SE_w²) / Σ(1 / SE_w²), and SE = (Σ 1 / SE_w²)^−½.
- One-sided 95% bounds: LB = d − 1.645·SE and UB = d + 1.645·SE, and likewise LB_w and
  UB_w.

The rule (design §3.7, verbatim):


**Pre-registration.**

- `decide.py` is `/data/scfix-o4/driver/decide.py`. Its sha256 is written into every
  plan as `x_decide_sha256` before the run.
- It reads `observations.jsonl` and `plan.json` (which carries the same-bytes list),
  computes §3.3, and writes `decide.json`.
- The driver's median statistics are still reported, but they decide nothing.

**VALID.** For each workload, compute the o4 / o4-aa HL estimate a_w with a two-sided
99% bootstrap interval.

- If that interval excludes 0, the workload is biased. Rerun that workload's campaign
  once with the seed + 100.
- If it is still biased, decide with a `reference_bias` flag recorded on every row.

**G0 (correctness).** All §3.2 correctness gates pass on all three workloads.
Otherwise X is excluded as `unsafe`, whatever its speed.

**ADD**, for add-ons A1, A3, A4, A6, A7 and A8, plus A2a if built. Accept X iff all of
these hold:

1. G0.
2. Holm across the family F of add-ons decided in A2 and H: sort the one-sided pooled
   p-values p = 1 − Φ(d / SE) in ascending order; X is accepted when every p up to and
   including X's satisfies p_(j) ≤ 0.05 / (|F| − j + 1).
3. Non-inferiority on every differing workload: LB_w > log(0.98).

**REMOVE**, for removals X1-X4, and **FIDELITY**, for I1. Accept (remove the component,
or include the rule) iff all of these hold:

1. G0.
2. UB ≥ 0: a loss is not shown.
3. LB > log(0.99): the pooled loss is under 1% at 95%.
4. LB_w > log(0.98) on every differing workload.

An item whose bytes equal o4's everywhere is removed (removals) or included (I1) for
free. A removal that also passes ADD is a speed gain in its own right.

**BEST (the B property).** In every campaign, every arm A other than o4 and o4-aa gets
pooled and per-workload one-sided p-values for "A faster than O4". A Holm family per
campaign covers all of them.

- Any rejection at 0.05 means a configuration is faster than O4. If it is a candidate,
  ADD normally accepts it already.
- Otherwise (a challenger or an anchor), it becomes the base candidate for O4-r2: O4
  must absorb whatever makes it faster, or document why it cannot be composed.
- `test_no_recorded_arm_beats_o4` fails in the meantime.

**Groups and conflicts.**

- **Host-inline (A4, A6, X1).** If several are accepted, take the highest pooled d.
  Within 0.3%, prefer X1, then A4, then A6.
- **X3 against the firmware items.** X3 applies only if no firmware add-on (A1, A7, A8,
  A5) is accepted. Otherwise the regions stay, and X3 is recorded as "removable,
  superseded by an accepted firmware add-on". I1 is moot under X3.
- **X2 and X4.** If X4 is accepted, X2 is moot.
- **A1, A7, A8 and I1** compose.

**Exclusions are recorded with their numbers.** Each gets d, SE, LB and UB, pooled and
per workload, with its Holm rank. They go into `scopt/o4.py`, `docs/o4-evidence.json`
and `docs/O4.md`. There are no silent drops.
